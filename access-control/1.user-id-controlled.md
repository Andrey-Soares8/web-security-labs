# Access Control — User ID Controlled by Request Parameter (IDOR)

## Contexto

A página de conta do usuário exibe dados sensíveis — incluindo a chave de API — baseando o acesso apenas no parâmetro `id` da URL. Não há verificação server-side se o usuário autenticado tem permissão para ver os dados do `id` solicitado.

**Lab:** [User ID controlled by request parameter](https://portswigger.net/web-security/access-control/lab-user-id-controlled-by-request-parameter)

---

## Exploração

Após login com `wiener:peter`, a URL da página de conta era:

```
/my-account?id=wiener
```

Substituindo o valor do parâmetro:

```
/my-account?id=carlos
```

A aplicação retornou a página de conta de Carlos, incluindo sua chave de API — sem nenhuma verificação de autorização.

---

## Impacto

Qualquer usuário autenticado consegue acessar dados de qualquer outra conta apenas alterando o parâmetro na URL. Em aplicações reais esse vetor expõe dados pessoais, chaves de API, histórico de transações e qualquer informação vinculada ao perfil do usuário.

---

## Mitigação

O servidor deve verificar se o usuário da sessão ativa corresponde ao `id` solicitado — nunca confiar no parâmetro da URL como controle de acesso. A lógica correta: `if session.user != requested_id → retornar 403`.

---

## Aprendizados

- IDOR (Insecure Direct Object Reference) é um dos vetores mais simples e mais comuns em aplicações reais — aparece consistentemente no OWASP Top 10.
- Parâmetros visíveis na URL nunca devem ser o único mecanismo de controle de acesso.
- O mesmo raciocínio aplicado aqui foi o que permitiu resolver o bypass de 2FA anteriormente — reconhecer o padrão entre labs é o que acelera a resolução de novos cenários.
